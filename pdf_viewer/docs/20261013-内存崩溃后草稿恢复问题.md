# 内存崩溃后草稿恢复问题

状态：已完成本地源码修复和生产构建，尚未部署到用户服务器。用户反馈浏览器出现 Out of Memory 后无法恢复云端草稿，可能没有出现恢复提示；当时实际打开的文件及弹窗情况尚不明确，不能把某一个代码问题认定为该次故障的唯一原因。

服务器侧已确认存在对应草稿，并据此恢复出 247 页、4684 条标注的可编辑 PDF。服务器生成副本时曾出现旧 annotations.json 优先读取的问题，重建后校验通过。本地已有的测试 PDF 为 236 页，不能替代该 247 页文件的故障证据。

## 已确认的代码问题

- 当前依赖是 React 19.2 和 Ant Design 5.28。启动恢复使用 `Modal.confirm`，其默认静态渲染器读取 `react-dom` 的 createRoot/render；React 19 已移除这两个旧入口。生产代码的可选调用静默跳过渲染，本机 Edge 实测完整 dirty 草稿仍在 IndexedDB 中，刷新后却没有启动恢复弹窗。这是当前版本中已复现的本机提示缺失原因；尚未核对事故时服务器实际构建版本。
- 正常打开 PDF 的附件读取未正确解析 PDF 引用和 PDFArray，回退遍历所有对象时会选中历史残留 annotations.json。合成 PDF 的当前附件目录指向新数据，正常打开仍可能读取旧数据。另一个已复现的情况是：小量标注导出写入新 Keywords，但旧的可达 annotations.json 仍在文件内，单纯优先读附件同样会读取旧版本。
- 云端时间不严格晚于本机草稿和 PDF 内标注时间时，恢复选项被隐藏。请求失败也直接退出，没有明确的恢复重试入口。
- 云端按浏览器本地用户键、PDF 指纹和项目查询。可编辑版导出会改变文件身份，原文件的草稿可能不再匹配。
- 云端恢复查询位于整份 PDF 的元数据解析之后，存在再次产生高内存峰值、尚未查询就崩溃的风险。
- 旧版本保存确认完成、新版本仍在上传时，状态可能显示已保存；Worker 对 HTTP 200 非 JSON 回执也会误判成功。以上均已用实际函数及受控输入复现。

旧附件优先读取不能单独解释恢复提示缺失：文件匹配且云端时间更新时，合成测试仍出现云端恢复提示。OOM 不应删除已成功保存的服务器草稿，但未完成的上传和关闭页面时的应急保存不能保证执行。

## 可靠结论

服务器已有可用于重建的草稿，说明“用户不能恢复”不能直接等同于“服务器草稿被 OOM 删除”。已复现的故障组合是：React 19 兼容问题导致本机启动弹窗不显示，云端草稿又被时间门槛隐藏，或因重开导出文件、浏览器用户键/项目变化而匹配失败。本机恢复还受 dirty 标志、文件匹配、分片完整性和仅在启动时提示的流程限制，因此两种恢复入口可以同时失效，而存储中的数据仍然存在。不能确定用户该次事故具体命中了哪一组合。

整份 PDF 的提前解析、错误的旧附件读取以及保存回执对应旧编辑版本，会增加问题发生或误判的机会。OOM 前尚未成功落盘/上传的最新编辑仍可能丢失，本次修复不能追溯生成从未保存的数据，也不代表所有 OOM 根因已经消除。

## 本次五项修复

1. **按导出标记读取 PDF 内标注。** Keywords 明确包含内联标注时读该数据；标记为 ATTACHMENT 时解析当前有效附件目录及引用。统一正常打开和编辑数据读取路径，不再扫描孤立历史对象选取旧附件。
2. **提供常驻恢复入口并修复弹窗兼容性。** 工具栏和右下角均可打开恢复窗口；本机、云端及已读取的 PDF 内数据分别列出。时间仅用于排序，较旧、相同或未知时间的匹配云端草稿也能恢复；查询失败有原因和重试按钮。“稍后恢复”不删除本机草稿。修复启动 effect 清理后不再提示的情况；在 `src/index.js` 中为 Ant Design 静态弹窗注册 React 19 的 createRoot 渲染及卸载，保留原弹窗逻辑。
3. **保留导出文件的原草稿身份并提前查询。** 新导出 PDF 的尾部注释保存原文件指纹、文档身份、原查询用户键及页数。选择同一项目后，改名或重新导出的文件可继续查询原草稿。只读取首尾样本和轻量身份信息，在整份 PDF 元数据解析之前提供恢复选择；选择恢复时跳过该元数据解析。
4. **按当前编辑版本显示保存状态。** 旧上传回执不会把尚未保存的新编辑显示为“已保存”；只有明确成功的 JSON 回执才确认保存。保留旧云端查询返回格式兼容性和原保存/查询地址。
5. **校验并保留本机恢复版本。** 同一 IndexedDB 事务读取草稿清单和分页数据，恢复前检查标注数量、页码及缺页，拒绝不完整版本覆盖工作区。本机保留每个文件最多 3 个历史检查点、总计最多 30 个，列表先读摘要，选中后才读标注内容。存储不足时优先继续保存当前草稿；查询失败时仍保留本机应急副本入口。

## 适用边界及现场核查

- 新身份信息只对本次修复后导出的 PDF 生效。旧导出 PDF 没有该信息时，应使用崩溃前的原 PDF、同一项目和原浏览器用户键查找；无法从旧文件中可靠推断原匿名用户键。
- 清理浏览器站点数据会同时清掉本机草稿和原用户键；更换浏览器、HTTP/HTTPS、服务器地址或端口，也可能改变本机存储和查询身份。已带身份的新导出 PDF 可提供原查询键，但本次没有改变服务器鉴权或增加跨用户搜索接口。
- 每个本机文件保留的历史副本属于恢复保护，云端仍只查询现有 latest 接口；没有新增云端历史版本能力。
- 需继续核对用户当时打开的原 PDF 或导出 PDF、实际项目、浏览器用户键以及原查询结果。本地 236 页 PDF 不能替代服务器那份 247 页、4684 条标注文件的事故复现；本机模拟验证也不能证明真实故障的全部原因。

## 后续：浏览器内存优化

修改前备份：`runtime/memory-optimization-20261013/source-before-20261013-162922.zip`。

本轮在已有大文件按需读取、矢量 LRU 和资源检查点之上补充四项优化，保留现有业务数据和草稿保存链路：

1. Web 文件的 PDF 标注解析放到专用 Worker，只返回可编辑标注和少量元信息；成功、失败、超时或切换文件后终止线程，释放源字节和 pdf-lib 文档对象。Worker 读取 File，不向主线程复制完整 PDF。保留不支持 Worker 的环境及 Electron 的原解析回退。修正相对部署路径下 Worker 动态资源的加载路径。
2. 常驻草稿保存 Worker 空闲两分钟或切换文档时释放克隆快照和增量基线。正在保存及超时后仍在写入的请求会等待 Worker 返回，不强行中止保存。下次保存重新发送完整分页数据，仍走原 IndexedDB 和云端接口。
3. 页面快照及预览缓存使用实际解码宽高估算 RGBA 字节，并与压缩文件字节一起计入上限。保留当前可见页；其余页可从磁盘或服务器重新读取。显示清晰度和 PDF 导出质量保持原设置。当前页单独超出预算时仍保留，以免清理造成空白。
4. 关闭恢复窗口后卸载窗口、清掉查询引用；无匹配版本的预查询也释放结果。合并与最新本机草稿完全相同的“打开前”版本，避免重复行把云端版本挤到下一页。持久化草稿、历史副本及当前标注不会因此删除。
