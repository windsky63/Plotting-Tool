# PDF 导出 array buffer allocation failed 修复

## 查明的内存风险

- `PDFDocument.embedPng()` 仅解码并登记图片，文档的 images 列表仍保留 RGB/Alpha 像素。此前将局部 annotImage 设为 null、清空 Canvas 并不能释放这部分内存。多页导出时会一直累积到最终 flush。
- `PDFWriter.serializeToBuffer()` 根据整份文件大小申请一个连续 Uint8Array，生成后下载又构造 Blob。上一版时间片优化没有改变这条分配路径。
- 部署端现有日志没有本次浏览器导出错误堆栈，因此无法断定本次错误究竟发生在 PNG 解码还是最终封装；两处已确认风险均处理。

## 修改

1. `src/App.js`：释放每页 Canvas 后，立即执行该图片的 `embed()`，使用库原有的无损压缩将其写入当前文档，并释放未压缩像素，不留到最后累计处理。
2. `src/utils/pdfSerialization.js`：仅标注版下载启用 Blob 分块封装。复用 pdf-lib 的文件结构计算、对象序列化和交叉引用表，避免申请整份 PDF 大小的 ArrayBuffer。正常工作块为 4 MiB；单个对象更大时按该对象大小分配，并记录最大工作块。
3. 可编辑版和普通保存仍使用原字节接口。标注绘制、画布尺寸、PNG 无损格式、原图纸、页面缓存及标注数据均不调整。
4. 新增 `window.__lastPdfExportStage`、`window.__lastPdfExportFailure`，只保存阶段和错误摘要，不持有 PDF/Canvas。成功的 `[PDF封装耗时]` 增加 `maxBufferBytes`，标注版模式为 `chunked-blob-writer`。

## 验证与限制

使用最多 12 页的小样本测试：新旧封装逐字节一致、透明通道及 RGB 压缩数据一致、分块输出可重新加载、包含旋转/裁剪/附件、对象编号缺口、大于工作块的单个对象、禁用整文件分配仍可成功。未执行 600 页实测。

这降低的是导出内存峰值，并非保证任意大文件在任意低内存设备上都不会 OOM。PDF 文档对象及压缩图像仍需内存，Blob 的内存/磁盘管理由浏览器负责。
